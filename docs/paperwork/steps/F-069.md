# F-069 — Conventions page

**Status:** `done`  
**Type:** `Documentation`  
**Goal:** G-012

## Job

The project gets its code conventions page at `docs/architecture/conventions.md`, titled **"Code conventions"**. It states, for every language in the project, how names are written, where a new file goes, the folder size limit, how file headers look, and which folders are exempt from a README. The protocol gets a blueprint that shapes this page for any project, and the protocol map lists the page as a standing file every project has. The architecture abstract and the doc map link to it. No code changes yet. Binding agents to the page and the Step-flow rules come in F-070, and the renames come in F-071 to F-073.

The conventions the page will state (approved with the Job):

| Area | Rule | Today |
|---|---|---|
| Java packages | `com.aethelgard.<module>[.<area>[.<chapter>]]`: lowercase, one word per segment, using the same word the architecture paper uses for that area, chapter or mechanism | `product` is flat; engine uses `diag`, `event`, `system` where the paper says `diagnostics`, `events`, `systems` |
| Java types | UpperCamelCase nouns or noun phrases. A class that carries out a process is named after the process (`Subduction`, `Orogeny`), never with a verb. No `I` prefix on interfaces. Acronyms are written as words (`HttpServer`, `CliRunner`) | 7 verb-named classes: `Subduct`, `RidgeCreate`, `TraceBoundaries`, … |
| Java members | Methods are lowerCamelCase verbs. Boolean queries start with `is`, `has` or `can`, except record accessors, which are named after the component. Fields, parameters and locals are lowerCamelCase. Constants and enum constants are UPPER_SNAKE_CASE | already consistent, apart from a few boolean queries |
| TypeScript / React | Component files and components are PascalCase (`MapTool.tsx`). Other modules are lowerCamelCase files (`host.ts`). Functions and variables are lowerCamelCase, types PascalCase, module constants UPPER_SNAKE_CASE, hooks `useX`. Next.js reserved names stay as the framework requires | already consistent |
| Rust | snake_case modules, files and functions; UpperCamelCase types; SCREAMING_SNAKE_CASE constants | already consistent |
| CSS | kebab-case class names and custom properties | already consistent |
| Where a file goes | One job per folder. A Java package holds one area, chapter or mechanism of the paper. In the web front, `app/` holds routes, `components/` React components, `lib/` non-React logic, and `test/` test helpers. **A folder holds at most 12 source files**, not counting its README, `package-info.java`, or tests kept beside the code; a folder over that limit is split by job | `product` holds 39 |
| Tests | Where test files live and how they are named stays on the **Tests** line of `program.md`, and the page points there. The page adds that Java test methods are lowerCamelCase sentences stating the outcome, with an `@DisplayName`, and that TypeScript `it` titles state the outcome | already consistent |
| File headers | The four header lines in each language's comment form: `/* * */` for Java, TypeScript, CSS and Rust; `<!-- -->` for XML; `#` for TOML; `REM` for `.cmd` scripts. JSON and lock files have none. A Purpose line states a responsibility, never a record id or history. Record ids appear in code only in the tests' "Proves" comments | 43 main files carry ids like "(F-060)"; a few files have no header |
| Exempt folders | Build output (`*/target/`, `ui/web/.next/`, `src-tauri/target/`, `src-tauri/gen/`); dependencies (`node_modules/`); tool internals (`.mvn/wrapper/`, `.tools/`); layout segments (`src/`, `src/main/`, `src/main/java/`, `src/test/`, `src/test/java/`, `src/test/resources/`, `com/`, `com/aethelgard/`, `ui/web/src/`); generated icons (`src-tauri/icons/` and below); the stored test world (`src/test/resources/worlds/`) | none of these have READMEs today |

The page also says it is living: whenever something new comes in that it doesn't cover, the agent adds the convention here.

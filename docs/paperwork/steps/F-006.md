# F-006 — User Input / Input View / User View

**Goal:** G-001  
**Status:** `done`

## Job (approved)

Add the user-facing layer in the **engine**: **User Input** with Persistent / Non-persistent kinds, an **Input View** the Pool samples once at `update`, and a **User View** that reads only the **settled** Pool after each Step and produces a frame.

**Out of scope:** Swing/windowing (F-008), CLI (F-007), Delete Request, non-finishing Systems, domain inputs.

**Skeleton decisions (approved):** named string actions; Persistent latches until consumed; Non-persistent only if held at staging; Input View frozen at Step start; User View is a read-only callback/port with recording sink in tests.

## Functional requirements (approved)

| ID | Requirement (measurable) | Status |
|----|--------------------------|--------|
| FR-1 | **User Input** register supports **Persistent** and **Non-persistent** actions; callers can press / release / (for persistent) observe latch until consumed. | met |
| FR-2 | At each Step start, engine stages an **Input View** from User Input. Pool `update` reads that view; all sampled inputs are one simultaneous set for that Step. | met |
| FR-3 | Non-persistent actions appear in Input View only if held at staging; Persistent actions appear if latched (even if physically released before staging) until consumed. | met |
| FR-4 | **User View** is invoked once per completed Step with the **settled** `PoolSnapshot` only (never mid-Step / pre-merge state). Relationship is read-only (no Pool writes from the view). | met |
| FR-5 | Tests can drive User Input and attach a recording User View without UI toolkits; F-002–F-005 behavior unchanged when no input/view wired (defaults). | met |
| FR-6 | Prior Steps stay green; `engine` still has no UI/CLI/`product` compile deps. | met |

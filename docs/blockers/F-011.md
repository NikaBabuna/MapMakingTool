# F-011 — Wider Pool field carrier + pluggable merge types

**Goal:** G-002  
**Status:** `done`

## Job (approved)

Widen typed field **values** to **`Object`**, and replace closed merge-type handling with a **pluggable `FieldMergeType` interface**. Engine keeps Static / Increment / Constant / Destructive as defaults (`FieldType` enum implements the interface). Custom merge types can be applied via schema without editing engine merge internals. Increment remains `Long`-only.

**Out of scope:** pluggable emissions (F-012), Delete Request default, product module, world data, making heartbeat `value` an Object.

## Functional requirements (approved)

| ID | Requirement (measurable) | Status |
|----|--------------------------|--------|
| FR-1 | Field values (Pool, config seeds, System writes, provenance, snapshots) use `Object` (Long still works via boxing). | met |
| FR-2 | Merge behavior is a public `FieldMergeType` interface; `FieldSchema` maps field → that interface. | met |
| FR-3 | Engine default implementations match today's Static, Increment, Constant, Destructive rules. | met |
| FR-4 | A custom merge type can be registered on a field and applied on conflict without editing engine merge internals / adding enum constants. | met |
| FR-5 | Non-`Long` values work with Static (or Destructive) defaults; settled snapshot can read them back. | met |
| FR-6 | Default Increment still sums `Long`s; non-`Long` Increment inputs fail fast. | met |
| FR-7 | Full prior suite green; engine has no UI/CLI/`product` compile deps. | met |
| FR-8 | Architecture + merge docs record Object carrier, merge-type interface, and how to add a custom type. | met |
